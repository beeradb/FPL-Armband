# Two measurements, 2026-08-11

Both were run after two subagents died repeatedly on API connection errors; the cells and the
scripts survived because each was committed before its analysis. The analysis below was done
directly, from the committed artefacts.

## 1. Did the expected-goals backfill move the cells the record's four-season figures were measured on?

**Yes, but only where it could, and it explains about a fifth of the drift people noticed.**

The six-season grid was adopted partly on "nothing recorded is invalidated", which rested on the
four shipped season pairs being byte-identical inside a six-season run. Review pointed out that
this establishes only *grid*-invariance — both sides of that check were today's code — and that
the expected-goals backfill repairs 2022-23's GW1-15 hole and rebuilds 2021-22's season aggregate,
**both inside the shipped four**. So the question was whether the record's own figures still
reproduce.

Two arms, `FPL_SWEEP_SEASONS=default` with `FPL_NO_XG_REPAIR=1` against unset, on the vice-captain
fallback — the comparison with a recorded figure to check against. 24 paired cells per arm, written as 48 rows — two variants over the same cells.

**Per-cell, not just per-mean:**

| | |
|---|---|
| paired cells that differ between repair on and off | **6 of 24** — every cell of 2022-23, and no other |
| rows that differ, counting both arms | 12 of 48 |
| which season they are in | **2022-23, all of it** |
| 2023-24, 2024-25, 2025-26 | **byte-identical**, every cell, every outcome column |

That is the shape the code predicts, and reading it as a confirmation rather than a discovery is
the honest framing: `xgRepairs` deliberately does **not** rebuild 2022-23's season aggregate, because
that total is already complete, so 2023-24's prior never moved and its cells could not have. The row
is a pipeline check that passed. ⚠️ It is also **conditional on the shipped prior settings** — one
index reads a prior through season aggregates but the recency index reads its weekly rows, so any
arm with `PriorMinutesHalfLife` or `PriorRateHalfLife` above zero would move 2023-24 too. Both ship
at 0.

⚠️ **And this cannot say WHICH of the two repairs did it.** `FPL_NO_XG_REPAIR` turns both halves off
together, so the −0.0108 is the sum of 2022-23's own GW1-15 weekly fill and its prior 2021-22's
rebuilt season aggregate. `FPL_NO_XG_AGGREGATE` is the narrower switch built for exactly this cell
and it was **not run**. One further arm separates them at no new design cost.

⚠️ **One provenance caveat, recorded rather than explained away.** The repair-off arm stamped
`dirty=true` and the repair-on arm `dirty=false`, at the same commit four seconds apart, so the two
arms are not *provably* the same source tree. The differing constants digest is expected — the
repair switch is fingerprinted, which is the point of it being in that list — and the uncommitted
file was almost certainly the scratch pairing script. Almost certainly is not a record; re-run both
arms clean if this is ever load-bearing beyond bookkeeping.

**Does it account for the recorded drift? Mostly not.**

| | vice-captain fallback, `HOLD` |
|---|---|
| recorded in the research notes | **+0.4634** points per gameweek |
| measured with the repair **off** (the pre-backfill state) | **+0.4210** |
| measured with the repair **on** | **+0.4102** |

⚠️ **"Today's default" would be wrong and was corrected: every row in this table is a FOUR-season
run.** Both arms were deliberately run on `FPL_SWEEP_SEASONS=default` to compare like with like
against a four-season record. The shipped default grid is **six** seasons, where the same test reads
**+0.4590** on `HOLD`. That figure rounds to the recorded +0.46, so quoting a four-season number as
the current one is the specific trap the six-season block in `CLAUDE.md` warns about.

The backfill accounts for **0.0108** of a total drift of **0.0532** — about **20%**. The remaining
80% is a change in the model, not in the data.

⚠️ **Read that fifth as arithmetic about this grid, not as a transferable share.** It is a 24-cell
mean that is **zero in 18 cells**, and of the six that move it is **positive in four**; the mean is
negative only because two cells swing about −0.33 each. SE 0.091, t = −0.48. Season-clustered
inference is degenerate — three of four season means are identically zero — so **do not quote a
clustered t for it**. The 20% is exact for this comparison on this grid and would not be expected to
reproduce elsewhere.

**And the number nobody wrote down is the larger one.** The same two arms say what the backfill is
worth in *points*: on 2022-23's six cells it is **+3.635 points per gameweek, about +138 over a
season** (SE 1.540, t = +2.36) — the same order as the double-gameweek bug, and roughly three times
this harness's median detection threshold. Meanwhile the **paired** comparison it perturbs moves by
0.4 points a season. That is the record's own rule — *a shared baseline shift cannot move a paired
comparison* — demonstrated across a level shift **three hundred times** the paired movement. It is
worth more than the fifth.

⚠️ **This paragraph originally named `cbffdd8` and `e51a56a` as the candidates, and BOTH WERE
WRONG.** The cause was bisected the same day to **`c76c0d8`**, which gave `blankRate` one estimator
where two implementations had disagreed by up to 0.45. It moved the figure from +0.462 to +0.419 in
one commit — about four fifths of the drift — and its immediate parent was probed directly to
confirm it. ⚠️ Note the channel is **selection, not belief**: the fallback fires on realised
minutes, and `blankRate` prices the bench slots, so it changed which fifteen was bought and hence
who wore the armband. See
"the +0.4634 is superseded" in [scoring-model.md](../../docs/notes/scoring-model.md).

**Worth keeping as a small lesson about how the candidates were chosen.** The two wrong names were
inherited from a review that listed commits touching scoring code. The right one was found by
asking a different question — *which commit touches the quantity this rule actually prices?* The
vice fallback's value depends on which fifteen is held, so the shortlist should have been "commits
that change how a squad is built", and `blankRate` prices the bench. **A mechanism-shaped shortlist beat a
diff-shaped one**, and the diff-shaped one was confidently wrong rather than merely unhelpful.

Per-season, the invariance is exact where it should be: 2023-24 reads +0.5203, 2024-25 +0.2524 and
2025-26 +0.6442 under **both** arms, to four decimals. The one season that moves is 2022-23, from
**+0.2672 to +0.2238** per gameweek — so the repair makes the fallback look slightly *less*
valuable in the only season it touches, and that is the whole of the −0.0108.

**Consequences.** `CLAUDE.md`'s advice that a recorded figure is reproduced with
`FPL_SWEEP_SEASONS=default` is incomplete — it also needs `FPL_NO_XG_REPAIR=1` — but adding it
recovers only a fifth of the gap. **The recorded +0.4634 is superseded by a model change**, rather than
reproducible with the right switches, and is now marked so at "the +0.4634 is superseded" in
[scoring-model.md](../../docs/notes/scoring-model.md) with the five-probe decomposition. In scale: 0.0532
points per gameweek is about **2 points over a season**, against a squad total near 2,200, so this
is a bookkeeping problem rather than a scoring one — the danger is a future reader treating a
figure as current, which is this project's documented failure mode.

## 2. Does a "75% chance of playing" flag mean 75%?

**No — the percentages are systematically optimistic, and that part is established beyond argument.
But "squaring them" is REFUTED as the correction, and it was refuted by my own denominator.**

`availabilityFactor` (`metrics.go:1857`) returns the flag divided by 100 — face value, because
until now nothing else was possible: the season archive is an end-of-season photograph and cannot
say what was flagged in week 12. The recovered captures pair *what was said before the deadline*
with *what the player then did*.

⚠️ **What this measurement does NOT settle is where the correction belongs, and the record has a
rule about exactly this.** What was measured is a **minutes** ratio. `availabilityFactor` multiplies
**`Score`** (`metrics.go:1530`), which is not linear in minutes — the appearance term runs through
`appearanceFactor` and the clean sheet through `playsSixty`, both of `ExpectedMinutes`, and the
defcon term is added per gameweek outside the rate. So applying 0.545 at `availabilityFactor` is a
different correction, of a different size, from multiplying minutes by 0.545. The standing rule:
*check what a multiplier multiplies before calibrating it* — the failure that made
`new_coach_penalty` read 0.93 when the honest answer was 1.0.

⚠️ **And `availabilityFactor` has a second branch this table cannot reach.** With no percentage it
falls to the status code and returns **0.5 for `d` (doubtful)** — a hard-coded guess. The "no flag"
row below pools status `a` with status `d`-without-a-percentage and is dominated by the former, so
it does not test the 0.5. The script records `status` on every row, so splitting that bucket is a
re-print rather than a re-measurement.

**Method.** 52,442 paired observations across the five seasons 2021-22 to 2025-26, of which
**51,598 are analysed** — every table below is on that figure, after the drop described next. A
player's baseline is his own rolling mean minutes over his most recent **unflagged** gameweeks
*earlier in the same season* (at least three, baseline at least 30 minutes) — point-in-time, and
never his own future. 844 observations were dropped from gameweeks whose evidence is a **single
crawl filed against two deadlines**, deduplicated on the crawl timestamp rather than on bytes.

The pre-deadline property is not an assumption: `capture.Backfilled.Write` refuses to store any
capture that cannot prove *from its own payload* that it predates the gameweek it is filed under.
⚠️ **One staleness channel is unchecked, though.** A capture is allowed to be *behind* — a crawl
whose own `is_next` is GW10 may be the best available evidence for GW11 — and in that payload the
flag is a statement about **GW10** while this pairing uses GW11's minutes. The timestamp dedup
removes the cases where one crawl served both weeks and misses the rest. The store measures this as
`EventsBehind` but discards the value rather than writing it to the manifest, so filtering on it
means re-parsing the stored payloads. Any attenuation here biases the ratios **toward** the nominal
flag, so the bias reported below would if anything be understated — but that is an argument, not a
check.

| flag says | actually played, as a share of his own normal minutes | n | blanked entirely |
|---|---|---|---|
| 0% | **0.011** | 6,226 | 98.5% |
| 25% | **0.085** | 688 | 88.5% |
| 50% | **0.256** | 721 | 66.9% |
| 75% | **0.545** | 1,919 | 42.4% |
| 100% | **0.997** | 27,036 | 11.9% |
| no flag | 0.965 | 15,008 | 11.7% |

flagged *because* he has been out, so his most recent **unflagged** week — the thing my baseline
averages — is systematically older for a flagged player than for a healthy one. Measured, and
reproduced independently:

|---|---|---|
| none | 1.04 | 0.1% |

| 75% | 2.17 | 14.0% |

| 25% | 4.00 | 39.5% |
| 0% | 6.13 | 55.2% |

Now the placebo — **unflagged** observations only, no doubt of any kind, split by how stale the
baseline is:

| baseline staleness | n | realised share of own baseline |
|---|---|---|
| 1 week | 38,688 | 0.992 |
| 2 | 2,508 | 0.994 |
| 3 | 626 | 0.943 |
| 4-5 | 477 | **0.776** |
| 6+ | 475 | **0.658** |

**A stale baseline depresses the ratio by a third with no flag present at all.** Flagged players sit
disproportionately in exactly those bins, so part of the shortfall is my denominator drifting rather
than FPL being optimistic.

**And the deeper error is which quantity I calibrated against.** `availabilityFactor` multiplies
`Score`, whose `ExpectedMinutes` is a **recency-weighted** index that counts the weeks a player was
absent *as zeros*. So by the time a player is four weeks into a doubt, the model has already marked
him down heavily. Calibrating the multiplier against his *pre-doubt healthy* level charges him for
the same absence twice — hardest at the 25% flag, where squaring over-corrects by **92%**.

Corrected, by two independent routes that agree: reweighting to the unflagged staleness mix, and
using a recency-weighted denominator that matches what the model actually does.

| level | as measured | staleness-reweighted | recency-weighted base | `flag²` |
|---|---|---|---|---|
| 25% | 0.085 | 0.120 | 0.120 | 0.062 |
| 50% | 0.256 | 0.296 | 0.319 | 0.250 |
| 75% | 0.545 | 0.598 | 0.579 | 0.562 |

Best-fit exponent in `realised = flag^p`: **1.84** on my denominator, **1.59** reweighted, **1.60**
against the recency-weighted base. Squaring needs 2.00. **So the square fits the one denominator
carrying the largest staleness bias, and over-corrects on the denominator that matters.**

⚠️ **This is the second instance of a pattern the record already names.** The appearance-curve refit
carries the rule *"a constant fitted against a proxy for its input is fitted to the proxy's noise
too."* Same failure in a different costume — and *"check what a multiplier multiplies before
calibrating it"* has now failed twice.

**What survives, and it is the substantial half:**

- **The direction is established beyond argument** — t = −13 to −24 against face value under every
  clustering tried, and it survived every attack: clustering by player, player-season or season;
  mean-of-ratios against ratio-of-means; window 4 to 38; floor 30 to 60; median for mean; points
  instead of minutes; and capture staleness, which if anything flatters the pooled figure upward.
- **A 75% flag is worth about 0.55 to 0.60**, on all three denominators — far below 0.75 either way.
- **The functional form is not established.** Suggestive at an exponent near 1.6.

The original table, on the uncorrected denominator, is kept below because the corrections above are
relative to it:

| flag | measured | model uses | flag² |
|---|---|---|---|
| 25% | 0.085 | 0.25 | 0.062 |
| 50% | 0.256 | 0.50 | 0.250 |
| 75% | 0.545 | 0.75 | 0.562 |
| 100% | 0.997 | 1.00 | 1.000 |

⚠️ **"It replicates in all five seasons" splits by level and must not be stated as one claim.** At
the 75% flag the five-season spread is **3.7%** — a genuinely tight replication. At 25% the level
spans a factor of **2.75** and declines monotonically (0.110 → 0.040), and at 50% it declines too.
What replicates at those levels is the *sign*, not the number — and by the same forward-looking rule
this record applies to the defender fixture swing, the 25% figure to use is nearer **0.04-0.05**
than the pooled 0.085, which is *below* the square, in the opposite direction to the staleness
correction. The two partly cancel and neither is pinned down.

| flag | 2021-22 | 2022-23 | 2023-24 | 2024-25 | 2025-26 |
|---|---|---|---|---|---|
| 25% | 0.110 | 0.110 | 0.097 | 0.053 | 0.040 |
| 50% | 0.299 | 0.319 | 0.229 | 0.208 | 0.214 |
| 75% | 0.526 | 0.553 | 0.573 | 0.544 | 0.527 |
| 100% | 1.033 | 0.981 | 1.000 | 0.978 | 0.986 |

The 75% and 100% rows are strikingly stable. The 25% and 50% rows drift downward over time —
worth watching, and a reason to prefer a shape over a fitted constant.

**Both tails.** Of players flagged 0%, **1.5% played at all** (averaging 51 minutes when they did).
Of players flagged 100%, **11.9% blanked** — identical to the 11.7% of unflagged players, so a
100% flag carries no information beyond "normal", which is what it should mean.

**Position.** Outfielders are indistinguishable from each other (0.53 to 0.54 at the 75% flag).
Goalkeepers read **0.699** at the 75% flag — difference +0.162, clustered t = **1.97** over 29
keepers, so *suggestive* and right on the line. It is not a staleness artefact: keeper gap matches
outfielders' and the result survives conditioning on a fresh baseline. ⚠️ **The 0.326 for keepers at
the 50% flag should not be quoted** — 25 observations from 14 players, a rough interval of 0.13 to
0.52.

**Status codes add nothing at 0%.** Injured, suspended, unavailable and not-in-squad all realise
0.000 to 0.024 of baseline. The percentage is sufficient there; the codes would only earn their
keep somewhere the percentage is absent.

**What this is, in this project's terms.** It is a **bias**: the model systematically over-rates
doubtful players' minutes, by about 38% at the 75% flag, 95% at 50% and threefold at 25%. Removing
a bias is the *safe* category for a search that picks the highest-scoring player — the same
category as the minutes-recency fix that worked — rather than the bias-for-variance trade that has
lost points five times here.

⚠️ **What would change my mind — and the first version of this paragraph named a test that CANNOT
FIRE.** It said the correction had not been replayed and that a null would mean the minutes floor
was already doing the job. **The replay cannot value this at all.** `PointInTime` builds each
element with `ID, Code, WebName, ElementType, Team, NowCost, Status` and **no
`chance_of_playing_next_round`**, and `statusAt` reconstructs only `a` and `u` — never `d`. So in
every replayed cell `availabilityFactor` is exactly 1.0 or 0.0: the percentage branch never runs and
the `d → 0.5` branch never runs. Squaring the flag would return **byte-identical seasons**, and by
this project's own rule that is not a null — *"a season that produces identical output under an
intervention is not a tie, it is a season where the intervention could not run."*

**So the honest status is `unmeasurable on this harness as wired`, not `unmeasured`.** It becomes
measurable the moment the recovered captures' flags are fed through `PointInTime` — the same seam
this document's own data came from — which is a **build**, not a sweep.

⚠️ **And the minutes floor could not have done the job it was credited with, on three counts.**
`MinExpectedMinutes` screens `SettledMinutes` — blended *historic* minutes per match — so the flag
never enters it; a player flagged 75% who started the last six weeks clears it comfortably. The
recorded "85-100% cliffed out" figure belongs to players who have **already missed a gameweek**,
where the same table reads **18%** for players still playing, which is the population a flag fires
on and the one this sample is built from. And the floor filters the **opening squad only** — the
transfer search ranks with no floor, and the weekly eleven and captain are picked from players
already owned.

**What the finding is worth in the meantime is on the live path, not the replay.** The percentage
reaches the agent directly through `PlayerMetrics.ChancePlay`, and the review protocol already tells
it to treat availability as a first-class filter. That is precisely the channel `blankRunFactor`
ships on despite being worth nothing measurable in the replay.

**And read the exposure per squad, not per player.** Flagged players (25/50/75) are **6.4% of the
analysed observations** — 3,328 of 51,598 — which sounds negligible. But the population here is
*established* players, roughly the pickable pool, so at that rate **a fifteen-man squad carries
about one flagged player in a typical week**. The share is small; the weekly exposure is not. ⚠️ An
earlier draft quoted "6.3%", which took the numerator after the repeat-crawl drop and the
denominator before it.

⚠️ **A neighbouring live constant overlaps this and the overlap is unmeasured.** `blankRunFactor`
(0.75) discounts **minutes** for a player one to three gameweeks into an absence, and was calibrated
on the *unflagged* population specifically so as not to double-count `availabilityFactor`. That
separation is weaker than it reads: the diagnostic's "flagged" test runs on `statusAt`, which never
returns `d`, so in the replay almost every doubtful player sat in the unflagged arm. Live, a flag
fires *before* the first missed gameweek and the blank run *after* it, so a player who is both would
be discounted twice — once on `Score`, once on minutes. Measure that before both are on at once.

## 3. The re-fit — withdrawn once, corrected, and the answer is a trend rather than a constant

⚠️ **This section reported 1.59 and that figure is WITHDRAWN.** Three reviews found two defects in
the program that produced it, both verified before correcting. The corrected answer is **about 1.35
pooled — and the pooled number is the least interesting thing in the table**, because per season the
exponent runs from **1.03 to 1.76**, rising.

**What was wrong.** First, the engine was not the engine that ships: the program called
`analysis.NewEngineFull` and attached neither `Engine.Recent` nor `Engine.Priors`, which every
engine inside `Simulate` attaches on the next two lines. With `Recent` nil there is no
recency-weighted minutes index and `blankRunFactor` never fires; with `Priors` nil the prior-season
blend returns early. So it measured the right *field* carrying its *fallback* value — the flat
season-to-date mean — while its write-up claimed to be "on the denominator that actually gets
multiplied", and the mechanism that write-up named for its headline result was **not switched on in
the run**. Second, a double gameweek posts a two-match minutes total against a per-match
expectation, and the doubles are not spread evenly across the rungs (9.96% of the 25% rung against
1.92% of the no-flag rung), so it did not cancel in the normalisation.

The two moved the answer in **opposite** directions — wiring the engine took 1.59 to ~1.41, the
doubles fix pushed back up — so neither could be ignored and they did not conveniently offset.

⚠️ **The way it slipped is the part worth keeping.** This project's rule is *"every engine that
scores players needs the index"*, enforced by `TestEveryScoringEngineGetsRecency` — which reads
`simulate.go` **only**. An engine built in `cmd/` is invisible to it. The rule held; the enforcement
had a seam. `backtest.EngineAt` now exists so the wiring cannot be omitted by a caller who does not
know to look for it, and the guard should be widened to glob `cmd/`.

The corrected run covers **six seasons and 59,123 observations** — the same grid as the replay's
default — rebuilding the model's view at each deadline through `backtest.EngineAt`, the replay's own
wiring, and pairing it with FPL's published flag and the player's realised minutes per match. It
runs in **7 seconds**: the first version re-parsed the whole capture payload once per player, about
130,000 times, and took over 25 minutes. ⚠️ Note this is still a **minutes** ratio while
`availabilityFactor` multiplies **`Score`**, which is convex in minutes — that caveat from section 2
is untouched here.

| flag says | realised ÷ expected | normalised | `flag²` | `flag^1.5` | n |
|---|---|---|---|---|---|
| 0% | 0.028 | 0.028 | — | — | 4,007 |
| 25% | 0.164 | **0.160** | 0.062 | 0.125 | 502 |
| 50% | 0.402 | **0.393** | 0.250 | 0.354 | 627 |
| 75% | 0.716 | **0.700** | 0.562 | 0.650 | 2,088 |
| 100% | 1.112 | 1.088 | 1.000 | — | 30,165 |
| no flag | 1.022 | 1.000 | — | — | 21,734 |

**Pooled exponent: 1.32 to 1.40** by reference group, **1.32 to 1.58** across the floor sweep, and
**1.46 to 1.54** once stale captures are dropped. Call it **≈1.45 with a band of 1.3 to 1.6**.

⚠️ **No interval was ever computed for it, and one specification's interval contains 2.00.**
Clustered by season — the honest estimator, three degrees of freedom, critical value 2.776 — the
best-defended specification (shipped denominator, captures within a day) gives **1.59 with a 95%
interval of [1.16, 2.03]**, i.e. `t` = −2.60 against squaring: **not rejected**. Squaring is
rejected on three of four specifications and survives on the one with the fewest known defects. The
point estimate spans **1.44 to 1.78** across those four — two and a half times the sensitivity range
this section previously offered as its robustness check.

**So "`flag²` is refuted" is withdrawn as well.** What is refuted, under every specification tried
and by a wide margin, is **face value** — `p` = 1.00, which is what `availabilityFactor` ships.

At the 25% rung squaring predicts 0.062 against 0.160 measured, and even `flag^1.5` over-corrects.
But the flag is worth **more** than every earlier pass said at every rung, and the discount is
milder than either 1.6 or 2.0.

⚠️ **Quote the rung values, not an exponent.** Three interior points cannot identify a functional
form. The fit is forced through an anchor the data put 6.7% away from 1.0; re-anchoring on the
measured 100% rung makes the per-rung exponents *rise* with the rung (1.61 / 1.79 / 1.89), which is
not what a power law does; and the 0% rung reads 0.028 rather than 0, so the family is wrong at the
bottom as well as the top. **The durable statement is that a 75% flag is worth about 0.65-0.70 of
expectation** — 2,088 observations, replicating in every season — and the exponent is a lossy
summary of that.

⚠️ **Two thirds of that fit is one rung.** Least squares on the log scale weights each rung by
`ln(flag)²`, so the 25% rung — **502 observations**, the smallest — carries **77%** of the answer, the
50% rung 19%, and the 75% rung with 2,088 observations just **3%**. The rung that dominates the fit
is also the one that replicates worst.

### The trend is NOT the finding — it is confounded with the archive

| season | 25% | 50% | 75% | exponent |
|---|---|---|---|---|
| 2020-21 | 0.257 | 0.425 | 0.744 | **1.03** |
| 2021-22 | 0.153 | 0.409 | 0.651 | 1.35 |
| 2022-23 | 0.198 | 0.429 | 0.696 | 1.18 |
| 2023-24 | 0.163 | 0.376 | 0.691 | 1.33 |
| 2024-25 | 0.097 | 0.351 | 0.765 | 1.62 |
| 2025-26 | 0.079 | 0.354 | 0.656 | **1.76** |

⚠️ **This section called that trend "the finding". It does not survive a filter aimed at a known
defect, and the defect improves monotonically across the archive.**

A capture is dated evidence and the dates are not equally good across seasons. Wayback coverage
gets better over time, so early seasons carry more captures taken long before the deadline — and a
stale flag has had time to be revised, which drags the rung toward the unflagged population and
pushes the fitted exponent **down**. That biases exactly the early seasons, in exactly the direction
that manufactures a rising trend.

`flagfit -maxlead 24` now drops any gameweek whose capture was taken more than a day before its
deadline. Nothing read `hours_to_deadline` before this, though every manifest has carried it:

| | per season | slope | t |
|---|---|---|---|
| all captures | 1.03 / 1.35 / 1.18 / 1.33 / 1.62 / 1.76 | **+0.132** | **4.35** |
| captures ≤ 24h | 1.34 / 1.94 / 1.10 / 1.33 / 1.86 / 1.76 | **+0.060** | **0.69** |

**The trend is gone.** Filtered, the exponents bounce rather than climb, and the earliest season —
which read 1.03, the number that made "face value was once right" so quotable — reads 1.34. The
pooled exponent also *rises* to **1.46-1.54**, because stale captures were biasing it down.

**Verdict: suggestive, not established, and confounded with an instrument property.** The filter is
not free either — it costs the thinnest rung about 13% of its observations, and a noisier estimate
is easier to flatten. But a claim that dissolves under a correction aimed at a known defect has not
earned "the finding".

**Standing rule for any future flag measurement: report `hours_to_deadline` and filter on it.** The
field was there all along and nothing read it.

### What survived correction, and what did not

⚠️ **"The model under-predicts healthy players by 9%" is WITHDRAWN.** That 1.091 was a *pooled*
reference inflated by double gameweeks. Corrected, players FPL says nothing about read **1.022** —
the model is calibrated on them to within about 2%. The 9% was roughly half doubles arithmetic and
half the pooling of two groups that disagree. It was not a second finding; it was the next
paragraph's finding, counted twice. The cause I nominated — the recency index carrying old absences
— was doubly wrong: the recency index was not in that run, and adding it *raises* the reference
rather than lowering it.

**And the no-flag group is clean**, which the earlier pass could not check: splitting it by status
shows all 21,734 rows are status `a`. There are no doubtful-without-a-percentage players diluting
the comparison group.

**An explicit 100% flag is not a null — it survives correction, much smaller, and it is not
actionable.** Those players return **1.112** of expectation against **1.022** for the unflagged: a
**9% gap**, not the 17% first reported.

⚠️ **And the two groups are not what this section assumed.** FPL's 100 is **sticky** — set once on
recovery and left for the rest of the season. Only about **10% of 100%-flag rows are the first week
at 100**, half have carried it five weeks or more, and **no player ever returns from a flag to the
no-flag group**. So the comparison is not "recovered" against "healthy"; it is **"has had any news
this season"** against **"never has"**, permanently — two groups differing in calendar position,
double-gameweek exposure and expected minutes before any flag is considered.

⚠️ **Corrected for all of that, it is worth about 2% among the players you would actually buy.**
Matching on gameweek, dropping doubles and using the shipped denominator takes the gap from +16.7%
to **+6.6%** — and it is concentrated at the fringe: **+11.8%** below 48 expected minutes against
**+1.3%** above 73. In the near-nailed band it is **+2.4%**, decaying from +6.2% in the first
fortnight to +0.4% after ten weeks. A flat correction of the headline size would be wrong by an
order of magnitude for most of the group it applies to. **Do not act on it.**

⚠️ **The mechanism is probably right and the evidence first offered for it argued against it.** On
the unwired season-average denominator the excess does **not** decay with weeks-since-flag at all —
which is what a denominator that never forgets produces. Only the properly wired recency denominator
gives the decaying profile the mechanism predicts (+20.6% fresh down to +3.0% after fifteen weeks).
Right conclusion, wrong instrument — the same failure the record already names about
`TestDiagSixtyMinutes`, in a diagnostic again. Section 2 concluded a 100% flag carries
"no information beyond normal" on a self-referential baseline; against the model's own expectation it
does carry information.

The mechanism is mundane once seen: FPL publishes "100%" about a player who was *recently doubtful
and has recovered*, and any minutes estimator built from his own record still carries the absence. So
the flag says the absence is over while the model still partly believes in it.

⚠️ **Three qualifications, because an earlier version called this "a buy signal" and that was an
action recommendation with nothing replayed behind it.** It is a gap in **minutes**, not points, and
`availabilityFactor` multiplies `Score`. It is the **smallest** mispricing per rung — the 25% rung is
over-priced by 56% (0.25 modelled against 0.160 realised) where 100% is under-priced by 9% — and only
the largest in **aggregate**, because it covers 30,165 observations. And nothing here prices it in
points, because the replay carries no percentages at all.

### What still stands from the review

Nothing here rescues the replay. `PointInTime` still carries no percentage, so the correction remains
**unmeasurable on this harness as wired**, and this pass does not change that — it changes what the
correction *should be* when someone wires it. The per-season replication also repeats the earlier
pattern and should be read the same way: tight at 75% (0.572 to 0.655 across five seasons) and
declining monotonically at 25% (0.137 to 0.056), so the forward-looking value at the lowest rung is
below the pooled figure.
